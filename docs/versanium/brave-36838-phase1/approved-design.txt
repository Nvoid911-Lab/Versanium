**3. eligibilityを確定**

Phase 1の対象は次に限定します。

- 通常のTabbed Activity
- HTTPS、host完全一致の`m.youtube.com`
- pathが`/watch`、空でない`v` parameter
- 生存中のowner Tab／WebContents
- 既存upstreamのfullscreen動画PiP条件を満たす
- Activityがfinishing／destroyed／config-change中ではない
- Minimized Custom Tabs／Actor PiPではない

JavaのURL判定は、Brave native helperと同等と主張しません。**既存fullscreen入口だけを使用する**ことによってnative helperを不要にします。

**4. controllerのstate machine**

| state | 意味 |
|---|---|
| `INACTIVE` | owner sessionなし |
| `ENTERING` | owner登録済み、framework entry確認待ち |
| `ACTIVE` | framework true callbackを受領済み |
| `EXITING` | 保護解除済み、owner cleanup／exit分類中 |

保持するsession情報は次のとおりです。

- process内で単調増加する`long generation`
- owner Activity identity
- owner `WindowAndroid` identity
- owner Tab identity＋tab ID
- owner WebContents identity
- entry origin：explicit／framework auto
- owner documentのnavigation epoch
- upstream entry処理済みflag
- cleanup開始／完了flag
- pending task、WebContents／Tab／MediaSession observer
- exit reasonとowner限定のmedia停止責務

遅延callbackは、**controller生存・generation・WebContents identity・必要なstate**を毎回照合します。tab IDだけで再取得して操作しません。

遷移は以下です。

```text
INACTIVE → ENTERING → ACTIVE → EXITING → INACTIVE
                 ↘ rollback → INACTIVE

INACTIVE → ACTIVE
           framework auto-entryのstrict adoption

ENTERING／ACTIVE → EXITING
                   tab変更・navigation・close・破棄など
```

同じownerのduplicate entryは既存generationを返し、新しいsessionを作りません。異なるownerへの置換は、旧sessionの終了を先に完了させます。

**config changeは、Phase 1ではactive sessionを復元しない方針を選びます。**

旧Activityはsessionを終了し、新Activityは`INACTIVE`から開始します。保存Bundleのactive flag／tab IDから保護状態を復元しません。新Activityにframework true callbackが来た場合だけ、通常のstrict adoptionを適用します。

これによりprocess death後のstale復元と、別windowへの誤rebindを防ぎます。config-changeをまたぐPiP継続はPhase 1の保証対象に含めず、安全に終了できることを試験します。

**5. explicit entryのexact sequence**

`VIDEO.attemptPictureInPicture()`内を次の順序にします。

1. 既存`canDoPictureInPicture()`を実行。
2. 対象Tab／WebContentsを一度capture。
3. 既存bounds／`PictureInPictureParams`を構築。
4. policy eligibilityとowner identityを再確認。
5. controllerへ`beginEntry(owner)`を通知し、`ENTERING`を登録。
6. **直後に既存framework `enterPictureInPictureMode()`を呼ぶ。**
7. trueならcallback待ち。ここでは`ACTIVE`にしない。
8. false／既存catch対象の例外なら、captureしたgenerationをrollback。
9. framework true callbackで`ACTIVE`へ確定。

rollbackはregistrationとobserverだけを解除し、通常fullscreenや再生状態を変更しません。

framework call中にtrue callbackが先行した場合、後から来たrollbackは`ENTERING`一致条件を満たさず、新しい状態を消しません。

callback未着への安全弁として、entry開始から**2秒**で状態を再確認します。framework PiP中なら確定処理へ、PiP外ならrollbackします。この値は修正の中心となるgrace periodではなく、孤立した`ENTERING`を残さないための上限です。

**6. auto-entryとの統合**

auto-entryはACTIVITYのtrue callbackで、explicit entryと同じsession型へ取り込みます。

- 既存`ENTERING`とowner一致：同じgenerationを`ACTIVE`へ
- 既存`ACTIVE`と一致：duplicate通知としてno-op
- `INACTIVE`：strict eligibilityを確認して新規adopt
- owner不一致／`EXITING`：旧sessionへ結び付けない

auto-entryでは、VIDEOのauto-PiP設定更新時に**直近のeligible owner snapshot**を保持します。これはactive sessionではなく、tab／WC／window／document epoch付き候補です。

callback時にfullscreen状態が遷移していても、同一documentの有効なsnapshotとframework PiP確認を使用できます。tab切替、WC交換、navigation、auto-entry無効化でsnapshotを破棄します。

callback前のHTML保護は、候補があるだけでは許可しません。**frameworkが既にPiP中と報告している場合**に限り、その候補を検証して暫定`ENTERING`へ取り込みます。単なるauto-entry設定ONでfullscreenを保持し続ける実装にはしません。

**7. Activity callback ordering**

既存Chromiumはtrue側でpersistent-videoを設定し、false側で登録済みleave callbackを実行します。この責務は維持します。[固定Chromium VIDEO](https://github.com/chromium/chromium/blob/1d17a2e2ee147bb7d6ae2ab6abdb3a2510c17775/chrome/android/java/src/org/chromium/chrome/browser/media/FullscreenVideoPictureInPictureController.java)

`ChromeActivity.onPictureInPictureModeChanged()`の順序を次に確定します。

| true側 | false側 |
|---|---|
| 既存`super` | 既存`super` |
| 既存Minimized Custom Tabs除外 | 既存Minimized Custom Tabs除外 |
| 既存Actor判定・除外 | controllerの`beginFrameworkExit()` |
| controllerでowner登録／adopt | 既存Actor exit callback |
| 既存`VIDEO.onEnteredPictureInPictureMode()` | 既存`VIDEO.onFrameworkExitedPictureInPicture()` |
| controllerのentry完了確認 | controllerのexit cleanup継続 |

false側では先に`EXITING`へ移し、fullscreen／dismiss保護を解除してからupstreamのpersistent false callbackを通します。

true側のduplicate callbackでは、owner sessionについて既存`onEnteredPictureInPictureMode()`の二重実行も防ぎます。他のPiP経路の既存動作は維持します。

`onNewIntentWithNative()`にも、既存VIDEO exit呼出より前にowner sessionの終了通知を追加します。これを省くと、upstreamだけ終了して専用sessionが残ります。[固定Chromium ACTIVITY](https://github.com/chromium/chromium/blob/1d17a2e2ee147bb7d6ae2ab6abdb3a2510c17775/chrome/android/java/src/org/chromium/chrome/browser/app/ChromeActivity.java)

**8. dismiss suppressionのreason matrix**

`dismissActivityIfNeeded()`では、**既存`updateAutoPictureInPictureStatusIfNeeded()`を先に実行します**。保護sessionが存在しても、実際のeligibility変更をAndroidへ通知する必要があるためです。

その後、owner policyを判定します。

| reason | Phase 1の扱い |
|---|---|
| `START` | owner一致＋`ENTERING`の有効期限内、または`ACTIVE`かつframework PiP中だけ抑制 |
| `RESUME` | 同上。framework PiP外ならexpand候補として終了へ |
| `LEFT_FULLSCREEN` | owner由来＋保護状態＋framework PiP中だけ抑制 |
| `WEB_CONTENTS_LEFT_FULLSCREEN` | 同上 |
| `NEW_TAB` | 保護解除、旧owner cleanup。新tabを裏へ送らない専用終了経路 |
| `CLOSE` | 保護解除、owner cleanup後にupstreamへ通す |
| `CRASH` | 同上。破棄済みWCへの操作は省略 |
| `REPARENT` | 旧windowでsession失効後、upstreamへ通す |

**reasonとActivityだけではowner判定が足りません。** VIDEOのtab／WC observerから、発火元Tab／WebContentsまたはcapture済みowner tokenをhookへ渡します。別tabのfullscreen終了をownerのtransient signalとして扱いません。

`NEW_TAB`ではupstreamの`moveTaskToBack(true)`部分をそのまま実行しません。旧owner停止・fullscreen解除・既存persistent callback排出を行い、新tabをforegroundに残します。これは単純なdismiss抑制ではなく、終了処理の置換です。

既存の遅延dismiss／unstash処理にも、所有sessionについてgeneration guardを追加します。旧sessionの遅延処理が次のsessionや新tabへ作用することを防ぎます。

**9. HTML fullscreen preservation**

`FullscreenHtmlApiHandlerBase.onHidden(tab, reason)`では、既存`onExitFullscreen(null)`の直前に判定します。

保持条件はすべてANDです。

- `tab == mTabInFullscreen == session.ownerTab`
- tab ID／WC identity一致
- handlerのActivity == owner Activity
- window identity一致
- ownerが生存、navigation epoch一致
- `ENTERING`の有効期間内、または`ACTIVE`かつframework PiP中
- tab switch／close／reparentによるhiddenではない

tab切替を意味するreasonは保持せず、旧owner終了を開始します。unknown reasonも保持しません。

STOPPED分岐でも、上記owner照合を`mTabInFullscreen`に対して行います。callback引数のActivityとhandler自身のActivityの一致も必要です。

`DESTROYED`のlistener解除は常に通します。fullscreen falseや新しいnavigationを受けた後に、古いowner flagだけで保護しません。[固定Chromium HTML](https://github.com/chromium/chromium/blob/1d17a2e2ee147bb7d6ae2ab6abdb3a2510c17775/chrome/android/java/src/org/chromium/chrome/browser/fullscreen/FullscreenHtmlApiHandlerBase.java)

**10. cleanup semantics**

共通入口を`beginExit(generation, reason)`に集約します。

1. generation照合。
2. `EXITING`へ遷移し、保護を即解除。
3. entry timeout／resume予定／候補snapshotを無効化。
4. 必要なowner media停止。
5. owner DOM fullscreen exit要求。
6. browser fullscreen UI解除。
7. upstream persistent-video leave callbackを一度だけ排出。
8. observer／locator／owner参照を解除し`INACTIVE`へ。

| trigger | 処理 |
|---|---|
| PiP expand | fullscreenを終了、再生は維持 |
| PiP X close | ownerを停止、fullscreen終了 |
| tab switch／new tab | 旧owner停止・fullscreen終了、新tabをforeground維持 |
| tab destroyed／crash | 即失効。destroyed WCへのAPI呼出なし |
| reparent | 旧session終了。新windowへ自動移管しない |
| navigation away | 同じWCでもsession終了 |
| WC交換 | owner置換として終了 |
| Activity非config destroy | owner停止を含め終了 |
| config destroy | 同じ終了経路。active復元なし |

navigationではprimary main-frameのcross-document commitを終了条件にします。同一documentでもYouTube watch URLの対象動画ID変更／対象外への遷移は終了します。

DOM fullscreen exitは`ownerWebContents.exitFullscreen()`を直接要求し、その後browser fullscreenを解除します。**effective fullscreen falseだけをDOM exit完了とは扱いません。**

通常exitはfullscreen observerを先に登録して、DOM exit通知または**500ms fallback**でbrowser UI cleanupへ進みます。tab切替・destroy等では新画面を阻害しないようbrowser UIを即解除します。browser側のupstream cleanupによる再度のexit要求があり得るため、保証するのは「専用cleanup transaction一回」であり、native呼出総数一回ではありません。

browser UI解除時には、managerがまだ旧ownerを保持していることを確認します。新tabのfullscreenを解除しません。[Brave controllerの終了処理](https://github.com/brave/brave-core/blob/4ea2dc54aaf5a404064cd9ff4473ee088a95fdb2/android/java/org/chromium/chrome/browser/media/BraveYouTubePictureInPictureController.java)

**11. expandとcloseの識別**

framework false callbackだけではexpand／closeを断定しません。

- false callback：まず`EXITING`
- owner Activityのresume確認：expandとして確定
- owner Activityのstop／finishing／destroy：closeとして停止
- 判定待ちが残った場合：**1,000ms後**に再確認
- foregroundへ復帰していなければowner停止
- 判定不明時はresumeしない

この期間もdismiss／HTML保護は解除済みです。遅延taskがowner Activity・generation・WCを照合し、次のsessionへ停止を持ち越しません。

screen-lockによるstopもPhase 1では通常停止側へ扱います。#39765相当の例外・unlock復元は追加しません。

**12. MediaSession policy**

**entry時のresumeは採用しません。**

通常fullscreen動画からのPiPは、既に再生している動画を引き継ぐ入口です。Braveのresume処理にはmanual entryやlock復元の背景もあり、今回の限定scopeへ無条件に持ち込むとuser pauseを上書きします。

Java MediaSessionのpaused通知だけでは、pauseの原因を確実に識別できません。「entry直前に再生していた」だけを根拠に後からresumeする方式も採用しません。

- 専用controllerからentry時resumeを呼ばない
- close／tab変更では保存したowner WCのMediaSessionだけをsuspend
- owner取得失敗時は操作を省略
- current tab fallback禁止
- upstream stash／unstashは維持し、owner session中はowner WCへ固定
- upstream `onStop()`の停止責務は維持
- `EXITING`中も必要な停止が終わるまでowner tokenを保持

VIDEOの`getMediaSession()`も、所有session中はowner WCを返す経路を追加します。所有sessionが失効した直後にcurrent tabへfallbackして、新tabの音声を止めないようにします。

PiPが安定してもYouTube自身のvisibility判定でpauseする場合は、Phase 1の観測結果として記録し、#33522へ分離します。

**14. Zoom共存とJava-only判定**

**Java-only：YES。新規C++／新規JNIは不要です。**

必要なAPIは既存Javaにあり、Javaからの`exitFullscreen()`／MediaSession操作が既存JNIを内部利用することは、新規JNI追加とは区別します。

PiP lifecycle判定は、必要な既存VIDEO呼出の直前に独立して追加します。Zoom patch入力・Zoom専用ファイル・設定・persistence・backupは変更しません。

`WebContentsImpl`のZoom fullscreen logicも変更しません。
